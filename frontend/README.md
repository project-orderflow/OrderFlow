# OrderFlow Frontend

Frontend операторской панели OrderFlow. Приложение построено на React 19, TypeScript и Vite; для интерфейса используется Ant Design, для маршрутизации — React Router.

## Архитектура frontend и авторизация

Точка входа: `src/main.tsx → App → app/AppProvider`. AppProvider подключает
TanStack Query, Ant Design и единственный RouterProvider из
`app/providers/router/appRouter.tsx`.

- `app`: провайдеры и маршрутизация; RequireAuth проверяет сессию перед показом защищённых страниц.
- `pages`: страницы маршрутов, включая LoginPage и UnauthorizedPage. Старые заготовки в `pages/ui` сейчас не подключены к роутеру.
- `widgets`: MainLayout, Sidebar и TopBar.
- `shared/api/client.ts`: общий fetch-клиент, Bearer-заголовок и типизированная ApiError. `shared/api.ts` делегирует ему get/post.
- `shared/auth`: хранение токена и запрос текущего пользователя через TanStack Query.

Публичные маршруты: `/login`, `/register`, `/unauthorized`. Остальные страницы защищены;
`/dashboard` перенаправляет на `/`. После входа пользователь возвращается
на исходный маршрут. Пока выполняется `/auth/me`, закрытые страницы не отображаются.

### Самостоятельная регистрация

Ссылка «Создать аккаунт» на странице входа открывает `/register`. После
подтверждения создания аккаунта сервером приложение возвращает пользователя
на вход с заполненным email.

Интеграция ожидает `POST /auth/register` с JSON `{ name, email, password }`
и ответом `201` с `{ id, email }`. Подтверждение пароля проверяется в форме.
Предварительные ограничения формы: имя до 120 символов, email до 255,
пароль от 12 до 128 символов. Backend определяет политику регистрации и права
нового пользователя. Интерфейс обрабатывает отказ в регистрации, дубликат
email (`409`), ошибки валидации (`400`/ `422`) и ограничение попыток (`429`).

При самостоятельной регистрации backend сохраняет имя и назначает роль
`OPERATOR`. При `404` или `405` форма сообщает, что сервер не поддерживает
регистрацию. Демо-seed из backend предназначен для проверки входа и каталога.

Контракт входа для backend из этого репозитория:

- `POST /auth/login`: JSON `{ "email": "...", "password": "..." }`,
  ответ содержит `access_token` и `refresh_token`.
- `GET /auth/me`: заголовок `Authorization: Bearer <token>`,
  ответ содержит `id`, `email`, `role` и `name`, если имя сохранено.
- 401 на защищённом запросе запускает `POST /auth/refresh` с JSON
  `{ "refresh_token": "..." }`. Сервер возвращает новую пару, а клиент сохраняет
  её и повторяет запрос один раз. При недействительной refresh-сессии
  открывается вход. 403 при входе или
  восстановлении сессии открывает Unauthorized. Сетевые ошибки и 5xx
  при восстановлении позволяют повторить запрос без удаления токена.

Пара токенов хранится одной записью localStorage `orderflow.session`
и доступна JavaScript. Пароль и профиль туда не записываются. Выход очищает
оба токена и query-кэш. Текущий backend не предоставляет маршрут отзыва
сессии при выходе. Для старой записи, в которой сохранён только access token,
потребуется один повторный вход после его истечения.

Проверки перед PR: `npm run build`, `npm run lint`, `npm run test:run`.
Тесты API и хранения сессии используют встроенный Node.js test runner (Node 24)
и подменённый fetch. Для проверки с настоящим backend нужны его контракт
и тестовая учётная запись.

## Запуск через Docker Compose

Для запуска полного окружения OrderFlow (Frontend, Backend и другие сервисы, описанные в Compose) необходим установленный и запущенный Docker Desktop.

Команды выполняются **из корневой папки OrderFlow**, где находится общий `docker-compose.yml`:

```powershell
docker compose --env-file .env.example up --build -d
```

Проверить состояние сервисов:

```powershell
docker compose --env-file .env.example ps
```

Посмотреть логи frontend:

```powershell
docker compose --env-file .env.example logs -f frontend
```

Посмотреть логи backend:

```powershell
docker compose --env-file .env.example logs -f backend
```

Остановить сервисы:

```powershell
docker compose --env-file .env.example down
```

Frontend открывается по адресу `http://localhost/` после запуска backend
и PostgreSQL. Nginx убирает префикс `/api` при проксировании, поэтому
`/api/auth/login` приходит в backend как `/auth/login`, а `/api/products`
как `/products`. Прямые ссылки на страницы админ-панели обслуживает SPA.
Docker и `dev:local` используют формат каталога backend из этого репозитория.

Если команда `docker` не распознаётся PowerShell, установи Docker Desktop для Windows, запусти его и открой новый терминал. Инструкция: <https://docs.docker.com/desktop/setup/install/windows-install/>.

## Типичные проблемы

### `docker` не распознана как команда

Docker CLI не установлен или недоступен в `PATH`. Установи и запусти Docker Desktop. Для разработки через `npm run dev` Docker не обязателен.

### API недоступен в Docker или `dev:local`

В Docker проверь состояние `backend` и `postgres` через `docker compose ps`.
При `dev:local` проверь, что `http://127.0.0.1:8000/health` доступен с хоста.

### Запросы блокируются CORS

Backend должен разрешать origin frontend. Для локального Vite это обычно `http://localhost:5173` (или фактический порт, указанный Vite). Настройка CORS выполняется на Backend.

### После изменения `.env` адрес API не изменился

Останови Vite (`Ctrl + C`) и запусти `npm run dev` заново.

### Вход завершается ошибкой

Проверь в DevTools браузера → Network запросы `/auth/login` и `/auth/me`, их HTTP-статусы и ответы Backend. Убедись, что используется правильный API URL и что тестовый пользователь создан на стороне Backend.

## Products и refresh-token flow

### Контракт backend

Контракт ниже принят на стороне frontend и требует согласования с backend.
Рабочее приложение не использует моковые товары.

- `GET /products` возвращает массив товаров; `GET /products/:id` — один товар.
- `POST /products` создаёт товар; `PUT /products/:id` обновляет его.
  Успех записи: JSON-ответ или 204; 403 — отказ в доступе; 409 — конфликт SKU.
- Товар: `{ id, sku, name, price, status, source }`. `id` — строка или число,
  `price` — конечное неотрицательное число, `status` — `active` или `inactive`.
  SKU и источник: 1–100 символов, название: 1–255; пробелы по краям удаляются.
  Валюта контрактом не определена, поэтому таблица не подставляет символ валюты.
- `/auth/me` может возвращать `permissions: string[]`, `role: string` или
  `roles: string[]`. Разрешения: `products:create`, `products:update`.
  Явный список permissions имеет приоритет, включая пустой список.
  При отсутствии permissions роли `admin` и `manager` разрешают обе операции;
  остальные пользователи могут только просматривать список, если backend разрешает GET.
  Backend обязан самостоятельно проверять права на каждом endpoint.

### Поведение интерфейса

Маршруты: `/products`, `/products/new`, `/products/:id/edit`.
Форма использует React Hook Form + Zod; список и карточка — TanStack Query.
После записи кэш инвалидируется и открывается таблица. Ошибка записи сохраняет
введённые значения. Есть loading, empty, error/retry, 404 и permission denied состояния.
Пагинация таблицы локальная, поверх полного массива ответа API.

При 401 параллельные запросы в одной вкладке используют один refresh. В браузерах
с Web Locks вкладки согласуют ротацию между собой. Запрос повторяется один раз
с новым access token. Повторный 401 завершает сессию, а 403 обычного запроса
не запускает refresh. При сетевой ошибке или 5xx пара остаётся доступной для
повторной попытки. Ротация сохраняет ключ query-кэша. Выход или новый вход
не позволяют запоздалому ответу заменить текущую сессию.

### Ручная приёмка с backend

1. Войти и проверить переход в админ-панель, затем открыть «Товары».
2. Проверить реальные ответы Network, обновить страницу, создать и изменить товар.
3. Проверить пустую таблицу, медленную загрузку, отключённую сеть и восстановление.
4. Истечь access token: проверить refresh и повтор запроса; истечь refresh token:
   проверить переход на Login. Проверить выход во время обновления токена.
5. Войти без прав редактирования: кнопки отсутствуют, прямой URL формы запрещён.
6. Вернуть 403, 404, 409 и 500 с backend и проверить соответствующие состояния.

Автоматические тесты используют подменённый fetch только в `tests/`.
Они проверяют refresh, конкуренцию запросов, хранение токена, схему товара,
права и методы/тела запросов API. Это не заменяет браузерную приёмку с backend.

## Заказы

Защищённая страница `/orders` загружает список через `GET /orders` с общим
API-клиентом. Ожидаемый ответ — массив объектов с полями `id`, `number`,
`external_number`, `source`, `customer`, `total`, `status`, `created_at`.
Идентификатор и номера могут быть строками или числами. Внешний номер может
отсутствовать или быть `null`. Источник, клиент и статус — строки, сумма —
число в основных денежных единицах, дата — ISO 8601 (дата или время с часовым
поясом). Валюта в этом контракте не задана.

Поиск по части внешнего номера без учёта регистра и фильтры по статусу и
источнику применяются совместно ко всему полученному списку перед разбивкой
на страницы. Варианты фильтров берутся из ответа API. Этот контракт предполагает
полный массив заказов и пока не подтверждён работающим backend.

Backend обрабатывает webhook и сохраняет заказ, после чего он становится
доступен через `GET /orders`. Пока список открыт в активной вкладке, TanStack
Query запрашивает его каждые 10 секунд и при возврате во вкладку.
Если заказ соответствует активным фильтрам, он появляется в списке при
следующем успешном запросе. Фильтры применяются перед пагинацией. При смене
фильтров открывается первая страница, а при сокращении списка отображается
последняя доступная страница, если текущая вышла за пределы списка.

Карточка `/orders/:id` открывается по номеру из таблицы, используя внутренний
`id` в URL. `GET /orders/:id` возвращает объект с полями заказа из списка и
следующими дополнениями:

- `customer` — объект с обязательным `name` и необязательными `email` и `phone`.
- `items` — массив позиций с `id`, `name`, `quantity` (положительное целое),
  `unit_price`, `total` и необязательным `sku`.
- `external_id` — строка или число, может отсутствовать. Это идентификатор
  в системе источника, отдельный от `external_number`.
- `subtotal`, `shipping`, `discount`, `tax` — необязательные числовые поля.
  Итоговая сумма берётся из обязательного `total` ответа.

Для источника `woocommerce` (без учёта регистра) карточка показывает бейдж
WooCommerce. Ответы 403 и 404 отображаются как отказ в доступе и отсутствие заказа.

## Склад и резерв заказа

Ожидаемые ответы backend:

- `GET /inventory` возвращает массив с полями `sku` (уникальный ключ),
  `name`, `on_hand`, `reserved` и `available`. Количества — целые числа.
  Низкий остаток выделяется при 1–5 доступных единицах, отсутствие — при
  нулевом или отрицательном доступном остатке.
- `POST /inventory/receipts` принимает `{ sku, quantity }` для существующего
  SKU, включая товары без текущего остатка. Quantity — положительное целое.
  При успехе ожидается JSON или 204. После записи страница заново запрашивает
  остатки. При ошибке форма сохраняет введённые данные.
- Для приёмки проверяется разрешение `inventory:receive` из `/auth/me`.
  Если `permissions` не задан, форма доступна ролям `admin`, `manager` и
  `operator`. Backend проверяет права на чтение остатков и запись приёмки.
- В `GET /orders/:id` статус резерва передаётся в `reservation_status`
  (`pending`, `reserved`, `partial`, `not_reserved`, `released`, `failed`),
  количество по каждой позиции — в `items[].reserved_quantity`, а код
  ошибки резерва — в `reservation_error`. Поля могут отсутствовать или
  быть `null`. Нулевой резерв отображается числом 0.
- `OUT_OF_STOCK` и `STOCK_CONFLICT` могут также вернуться в JSON ошибки
  HTTP как `{ code }`. Интерфейс показывает сообщения на русском.

Этот контракт складского API и полей резерва нужно сверить с backend.

## Тестовая оплата заказа

Ожидаемый контракт backend:

- `GET /orders/:id` возвращает `payment` (объект или `null`) и
  `can_create_test_payment` (boolean). Флаг должен учитывать права оператора и
  состояние заказа. Без явного `true` создание недоступно. При статусе
  `pending` или `succeeded` интерфейс скрывает создание даже при `true`.
- `POST /orders/:id/payments/test` получает `{ return_url }` с адресом карточки
  и возвращает объект платежа. Backend валидирует адрес возврата, использует
  sandbox провайдера, берёт сумму из заказа и проверяет права и возможность
  оплаты. Запросы из разных вкладок должны обрабатываться атомарно: для заказов
  с активным или успешным платежом backend не создаёт дубликат и возвращает
  существующий платёж или 409.
- Объект платежа содержит `amount` (число в основных денежных единицах),
  `provider`, `status` (`pending`, `succeeded`, `canceled`, `failed`),
  необязательные `external_id`, `currency` (трёхбуквенный код) и `confirmation_url`.
  Кнопка перехода доступна для `pending` с HTTPS-ссылкой или HTTP на loopback
  для локальной разработки.
- Backend сохраняет изменения статуса после webhook. Карточка перечитывает
  заказ при открытии, возврате во вкладку или восстановлении из истории
  и каждые 5 секунд, пока открыт ожидающий платёж. Сканирование прекращается
  при конечном статусе.

Для сквозной проверки создать тестовый платёж, перейти к провайдеру,
вернуться в карточку и дождаться статуса от backend. После успешной оплаты
создание и переход скрыты. Контракт и сценарий нужно подтвердить с
реальным backend и тестовым окружением провайдера.

## Сборка, упаковка и история заказа

Экраны `/picking` и `/packing` работают через ожидаемый API:

- `GET /fulfillment/{picking|packing}` возвращает массив записей с полями
  `order_id`, `order_number`, `item_count` (количество позиций),
  `priority` (`low`, `normal`, `high`, `urgent`),
  `status` (`pending`, `in_progress`, `completed`),
  `version` (неотрицательное целое или непустая строка) и
  `allowed_actions` (массив из `start`, `complete` с учётом прав оператора).
  Номер и идентификатор заказа — строка или число.
- `POST /fulfillment/{picking|packing}/:orderId/{start|complete}` принимает
  `{ version }` из записи в момент открытия подтверждения. Backend проверяет
  права и версию атомарно, выполняет переход `pending → in_progress → completed`,
  записывает событие и возвращает JSON или 204. После сборки backend добавляет
  заказ в очередь упаковки. При устаревшей версии или недоступном переходе
  возвращается 409. Интерфейс сообщает о конфликте, перечитывает очередь и
  обновляет кэш второй очереди, списка и карточки заказа.
- `GET /orders/:id` включает `events`: массив событий с уникальным `id`,
  `category` (`order`, `payment`, `reservation`, `picking`, `packing`),
  `occurred_at` (ISO 8601 с часовым поясом), `title` и необязательным
  `description`. Интерфейс сортирует полученные события от ранних к поздним.
  При одинаковом времени с точностью до миллисекунды сохраняется порядок backend.

Сквозная проверка с backend включает сборку и упаковку одного заказа, сверку
событий в его карточке и попытку подтвердить одно действие из двух сессий.
